## A 档 · 影响数据结构，请优先拍板

### A1. 向量维度是否全局统一？

| 项 | 内容 |
|---|---|
| 我的默认 | **全局统一**，由系统参数 `rag.embedding.dimension`（默认 1536）锁定。创建知识库时若所选 embedding 模型维度 ≠ 全局维度，直接拒绝（`40006`）。 |
| 原因 | pgvector 的 `vector(N)` 列维度固定，无法在同一列存不同维度向量。 |
| 代价 | 若未来想用 1024 维（如 bge-m3）和 1536 维混合，需要"全库重建"或改表结构。 |
| 备选方案 | ① 每个知识库一张分片表（表数量爆炸，不推荐）；② 按维度分表 `kb_chunk_1536` / `kb_chunk_1024`（复杂但可行）。 |
| **需你确认** | 是否接受"全局统一维度"？还是要求多维度并存？ |

### A2. 中文 BM25 分词方案

| 项 | 内容 |
|---|---|
| 我的默认 | DB 侧用 `to_tsvector('simple', content)` 生成 `tsv` 列（零依赖），**中文召回效果有限**。 |
| 备选方案 | ① 自定义 PG 镜像装 `zhparser` / `pg_jieba`（推荐，效果好，需改 Dockerfile）；② 应用层 Jieba 分词后写入（`tsv` 改为应用维护的普通列）；③ 放弃 BM25，仅纯向量。 |
| 影响 | `03` 中 `kb_chunk.tsv` 的定义方式；部署复杂度。 |
| **需你确认** | 选 ① / ② / ③？是否有运维限制（不能自定义镜像）？ |

### A3. 是否需要引入 Redis？

| 项 | 内容 |
|---|---|
| 我的默认 | **不引入**。Refresh Token 状态、登录失败计数、系统参数缓存均落地 PostgreSQL / 应用内存。 |
| 代价 | ① 每次刷新令牌查库；② 多实例部署时应用内存缓存不一致（需定时刷新或每次查库）；③ 登录失败计数有并发写热点。 |
| **需你确认** | 是否允许引入 Redis？未来是否多实例部署？ |

### A4. 是否需要引入消息队列？

| 项 | 内容 |
|---|---|
| 我的默认 | **不引入**。文档摄入、Schema 同步用应用内 `ThreadPoolTaskExecutor` + DB 状态机；应用重启时扫描中间态任务恢复。 |
| 代价 | 任务不可跨实例负载均衡；大批量摄入时占应用线程。 |
| **需你确认** | 是否接受？预估峰值摄入量（同时上传文档数）多大？ |

### A5. 权限矩阵中 ADMIN 的边界

| 项 | 内容 |
|---|---|
| 我的默认 | `ADMIN` 可管理**全平台**知识库 / 数据源 / 会话（即"越权可见他人资源"），但**不能**管理用户、模型、系统参数。 |
| 风险 | 数据源含生产库连接信息，ADMIN 全可见可能超出预期。 |
| **需你确认** | ADMIN 是否应只能管知识库，不能管数据源？或反过来？ |

### A6. 大整数精度

| 项 | 内容 |
|---|---|
| 我的默认 | `bigint` 计数（如 `rowEstimate`、token 数）以 JSON **number** 返回。 |
| 风险 | JS `Number` 安全整数上限 2^53，超过则精度丢失（如超大表的 row_estimate）。 |
| 备选 | 统一把 `bigint` 序列化为 **string**。 |
| **需你确认** | 是否统一改 string？（会影响前端类型定义） |
