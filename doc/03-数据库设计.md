# 03 · 数据库设计

> 返回 [索引](./README.md) · 上一篇 [技术架构设计](./02-技术架构设计.md) · 下一篇 [API 接口规范](./04-API接口规范.md)
>
> 目标库：PostgreSQL 16+，**全库只需要 `vector`（pgvector 0.7+）一个扩展**。
> 中文 BM25 分词在应用层用 Lucene 完成，数据库侧使用 PG 内置的 `simple` 文本搜索配置，
> **不安装 zhparser / pg_jieba 等任何需要编译的扩展**（见 §4.5）。
> 所有表使用 `bigint identity` 主键；可编辑资源维护 `updated_at`，流水/消息等记录以 `created_at` 为主（`timestamptz`）。
> 可执行结构以 `backend/src/main/resources/db/migration/` 下的 Flyway 迁移为准，附录 A 用于查阅。

## 0. 迁移落地与边界

- `V1__init.sql`：已定义的 5 张系统表、初始管理员和 20 个系统参数，保留原文件以避免已部署环境 Flyway 校验失败。
- `V2__business_tables.sql`：新增 13 张业务表及 pgvector 扩展，当前迁移最终共 18 张业务/系统表（不含 Flyway 自身历史表）。不重复创建系统表或写入种子数据。
- 新库顺序执行 V1、V2；已成功执行 V1 的库只执行 V2，由后端启动时 Flyway 自动处理。不要手动执行附录 DDL 后再启动 Flyway。
- 本次不调整 Docker、数据库连接或 Flyway 配置。迁移前核对目标库的 Flyway 历史；对于仅预装扩展的非空 schema，需检查基线是否会跳过 V1；若已手工创建系统表却没有 Flyway 历史，先核对其与 V1 一致，再处理基线，不能直接套用空库流程。
- 不改变既定产品范围：`visibility` 预留，单数据源单 schema，会话 `kb_ids bigint[]` 保持设计和 API 约定。

数据库保证：每类模型最多一个默认；embedding 维度为 1024；同一文档分片序号唯一；分片知识库与文档归属一致；切分参数、权重、计数和连接参数合法。Schema 同步状态独立于连接状态，持久化 `sync_status`、`sync_started_at`、`sync_finished_at`、`sync_error_msg`，供同步任务和状态接口共同使用。

应用层必须保证：模型引用类型正确（EMBEDDING/RERANK/CHAT）、资源归属鉴权、`kb_ids` 存在性和删除后的清理、仅 assistant 消息允许反馈/引用、文档摄入及 Schema 同步状态流转与并发幂等、各类冗余计数更新。`rag.embedding.dimension` 必须保持 1024；调整维度需迁移向量列和索引，不能只修改系统参数。

删除语义：子资源级联删除；模型或用户仍被资源引用时阻止删除，先转移/清理资源。删除分片后引用的 `chunk_id` 置空，`snippet` 与原 `document_id` / `kb_id` 保留历史快照，因此后两者不声明外键。SQL 会话随数据源删除；删除口径知识库仅清空 SQL 会话的 `kb_id`。

以下字段未在现有 V1/V2 与附录 A 中落地；须新增版本迁移，不能修改历史迁移或把文档参考 DDL 当成升级脚本。表总数暂保持 18 张。

| `sql_message` | `result_rows jsonb` | 保存实际返回的截断结果，历史查询不重跑 SQL；随消息删除，保留策略清理后为 null |

Refresh Token 以 `sys_refresh_token` 为权威，Redis 仅缓存活跃状态；每次刷新必须在数据库事务中校验未吊销、未过期并原子轮换旧令牌，提交后更新缓存。缓存丢失时查库，不能把缺失直接判成吊销，也不能仅凭缓存接受已吊销令牌。禁用、改密等即时 Access Token 失效的新增机制见 08，仍为待实现。

## 1. 命名与通用约定

| 约定 | 说明 |
|---|---|
| 表名 | 小写下划线，模块前缀 `sys_` / `llm_` / `kb_` / `chat_` / `sql_` |
| 主键 | `id bigint generated by default as identity primary key` |
| 外键 | 显式声明 `ON DELETE CASCADE`（子资源）或 `RESTRICT`（被引用资源） |
| 时间 | `created_at timestamptz not null default now()`；`updated_at` 由触发器或应用维护 |
| 软删除 | **不使用**软删除（除特殊说明），删除即物理删除；审计由 `sys_operation_log` 承担 |
| 热状态 | Refresh Token 活跃缓存（数据库为权威）、登录失败计数、系统参数缓存放 **Redis**；`sys_refresh_token` / `sys_login_attempt` 两张表保留作为审计与故障恢复 |
| 布尔 | `boolean` |
| 枚举 | 用 `varchar` + 应用层枚举 + `CHECK` 约束（避免 PG 原生 enum 的迁移成本） |
| JSON | `jsonb` |
| 密文 | `*_cipher text`（AES-GCM 加密后的 Base64），密钥来自应用配置 |

### 4.5 `kb_chunk`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | PK |
| kb_id | bigint | FK，冗余便于按库过滤 |
| document_id | bigint | FK，`ON DELETE CASCADE` |
| chunk_index | int | 文档内序号，从 0 开始 |
| content | text | 分片正文 |
| token_count | int | token 数 |
| embedding | vector(1024) | 向量，维度由全局参数固定 |

| metadata | jsonb | 章节标题、页码等 |
| created_at | timestamptz | |

`tsv` **不再使用生成列**。原设计依赖 `zhparser` 扩展 + `to_tsvector('chinese', content)`，
该方案需要编译安装扩展、且在 Windows 上不可用，已废弃。现改为：

```sql
-- 列定义：普通列，由摄入管线显式写入
tsv tsvector
```

写入与查询的两侧口径（分词器必须是同一个 `ChineseTokenizer` 实例）：

```sql
-- 写入侧（应用层先调用 Lucene smartcn 分词，得到 '我 爱 北京 天安门'）
INSERT INTO kb_chunk (kb_id, document_id, chunk_index, content, token_count, tsv, metadata)
VALUES (:kbId, :docId, :idx, :content, :tokens,
        to_tsvector('simple', :tokenizedContent), :meta);

-- 查询侧（查询串同样先分词）
... WHERE c.tsv @@ plainto_tsquery('simple', :tokenizedQuery)
```

> 使用 PostgreSQL **内置**的 `simple` 配置 —— 它按空格切分，
> 我们喂进去的已是分词后的词元序列，因此无需任何第三方扩展。
> 分词实现见 [`02-技术架构设计.md`](./02-技术架构设计.md) §5.7.1。

## 5. 索引设计

| 表 | 索引 | 目的 |
|---|---|---|

## 6. 文件存储布局（本地文件系统）

原设计的 MinIO（S3 兼容对象存储）已废弃，改为本地文件系统，通过 `StorageService` 接口访问。
数据库侧**只存相对路径**，不存绝对路径 —— 换个部署机器迁移根目录时无需改数据。

| 项 | 约定 |
|---|---|
| 存储根目录 | `wenqu.storage.local.root`，默认 `${WENQU_DATA_DIR:./.wenqu-data}/storage` |
| 相对路径 | `kb/{kbId}/doc/{yyyy}/{MM}/{uuid}.{ext}`，写入 `kb_document.file_key` |
| 落盘文件名 | 由服务端生成 UUID，不采用用户原始文件名（防路径穿越 + 规避中文编码问题） |
| 下载方式 | **后端鉴权接口**流式返回，无预签名 URL（见 [`04`](./04-API接口规范.md) §6.6） |
| 删除 | 删除 DB 记录后异步删除文件；失败由孤儿文件清理任务兜底 |
| 上传大小限制 | 单文件 50MB，单次 20 个（应用层 + 前端双重限制） |

**实际落盘示例**

```
.wenqu-data/
└── storage/
    └── kb/
        ├── 12/
        │   └── doc/2026/10/8f3a1c2e-....pdf
        └── 13/
            └── doc/2026/10/b7d90e4a-....docx
```

> 备份整个 `.wenqu-data` 目录即可；代码库需在 `.gitignore` 中排除 `.wenqu-data/`。

### 附录 A.1 混合检索参考 SQL

```sql
-- 向量召回（余弦距离 → 相似度 = 1 - distance）
SELECT c.id, c.document_id, c.kb_id, c.content, c.metadata,
       1 - (c.embedding <=> :queryVector) AS vector_score
FROM kb_chunk c
JOIN kb_document d ON d.id = c.document_id
WHERE c.kb_id = :kbId
  AND d.status = 'READY'
  AND c.embedding IS NOT NULL
  AND 1 - (c.embedding <=> :queryVector) >= :scoreThreshold
ORDER BY c.embedding <=> :queryVector
LIMIT :candidateTopK;

-- 全文召回（ts_rank_cd，并非 BM25；BM25 为保留的 API 枚举名）
-- ⚠️ :tokenizedQuery 不是用户原始问句，而是经应用层 Lucene 分词后的词元串，
--    如 '北京 天安门'。写入与查询必须用同一个分词器，否则召回失效。
SELECT c.id, c.document_id, c.kb_id, c.content, c.metadata,
       ts_rank_cd(c.tsv, plainto_tsquery('simple', :tokenizedQuery)) AS bm25_score
FROM kb_chunk c
JOIN kb_document d ON d.id = c.document_id
WHERE c.kb_id = :kbId
  AND d.status = 'READY'
  AND c.tsv @@ plainto_tsquery('simple', :tokenizedQuery)
ORDER BY bm25_score DESC
LIMIT :candidateTopK;
```

> RRF 融合在应用层完成：`rrf = Σ weight_i / (k + rank_i)`，`k` 默认 60。
> `score_threshold` 仅在向量支路按 `1 - distance` 过滤；不对原始 RRF 分或全文/重排分套用该阈值。融合后先取 `rerank_candidates` 重排再取 `top_k`；不开重排直接取 `top_k`。详见 02 §5.4。
